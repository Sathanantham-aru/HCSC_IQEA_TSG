### Instructions (Strict)

1. **Page tagging (MANDATORY)**
   - Prefix EVERY "Test Case Name" with the report page in square brackets, e.g. `[Page 1 - Summary Dashboard] Verify Executive KPI banner renders`.
   - A test case must never mix visuals from two different pages. If an interaction spans pages (navigation), tag it with the page where the action starts.

2. **Prerequisite / Setup Steps**
   - Every test case must include proper prerequisites (valid workspace access, report opened, dataset refreshed, appropriate RLS role) and navigation to the correct page before the main steps.
   - Step 1 always covers opening/navigating to the correct report page; the final step returns the page to its default state (clear filters / reset slicers) unless the case ends in an error state.

3. **Per-Page Report-Load / Initial-Render Validation (MANDATORY, one per page)**
   - For each page, add a case that verifies ALL visuals on that page render successfully on initial load — no blank/empty visuals, no persistent spinners, no load/query errors, and default slicer selections are applied.

4. **Visual Presence, Type & Position Validation (MANDATORY, one+ per visual per page)**
   - For EACH visual on each page: verify it is present, verify the visual TYPE matches the spec (e.g. MARKET = horizontal bar, SEGMENT = donut, Manager Scorecard = matrix, Strategic Quadrant = scatter), verify its POSITION matches the layout, and verify titles/axis labels/legends/data-labels/conditional formatting read as specified.

5. **Slicers, Filters & Date Boundary Validation**
   - Verify each slicer (REGION, SEGMENT, ORDER_DATE range, etc.) is present, has the correct default, and lists expected values.
   - Verify single selection, multi-selection, "Select all", and Clear/Reset update dependent visuals correctly.
   - **Date slicer BVA (MANDATORY):** for range date slicers, add explicit boundary cases — minimum date, maximum date, single-day selection, full-range selection, and out-of-range/invalid selection (use the exact min/max dates from the requirements or wireframe when available, e.g. 01/01/2011 to 31/12/2014).

6. **Cross-Filtering / Cross-Highlighting (MANDATORY, broad coverage)**
   - Build a cross-filter matrix: for EACH interactive visual on a page (treemap, donut, bar, matrix row, scatter bubble, stacked column, etc.), add a case that selects/clicks a data point in that visual and verifies the OTHER visuals on the page filter or highlight correctly.
   - Do NOT settle for one or two cross-filter cases — cover every interactive visual as a filter source where the report enables interactions.

7. **Filter Persistence Across Page Navigation (MANDATORY)**
   - Add cases that set slicer/filter selections on one page, navigate to another page and back, and verify whether filter state is retained or reset per the report design. Cover both "persisted" and "reset" expectations where the spec implies them.

8. **Visual Header Actions (across all major visuals)**
   - For each major visual (Top/Bottom Products, Matrix, Scatter, Treemap, Line, MARKET bar, donuts, stacked column), verify header actions where supported: Focus Mode, "Show as a table", "Export data", and Sort options (ascending/descending on the correct field).

9. **Interaction & Drill Behavior**
   - Verify drill-down/drill-up on hierarchical visuals (e.g. Matrix REGION → PERSON), drill-through to detail pages, tooltips on hover, and sorting.

10. **Data Accuracy Validation**
    - Verify KPI/Card values, chart aggregations, table/matrix totals & subtotals, and Return Rate/Profit Margin calculations match the requirements. Verify number/date/currency/percentage formatting.

11. **Negative & Operational Failure Scenarios (MANDATORY)**
    - Cover dataset refresh failure, individual visual rendering failure, query timeout behavior, empty/no-data result state for a filter combination, and permission/RLS-restricted access. Verify graceful error messaging in each case.

12. **Testing Techniques**
    - Apply BVA (slicer ranges/dates), Equivalence Partitioning, Decision Table, and State Transition where they add value.

### Output Format (Strict)
- Output strictly as a **Markdown table** with exactly these 7 columns, this header, in this order:

| Test Case Name | Step Number | Test Step Description | Test Step Expected Result | Status | Type | Category
   - **Test Case Name** = page-prefixed name (see rule 1). Repeat the FULL test case name on every step row of that test case.
   - **Step Number** = a SINGLE integer for that one row (1, then 2, then 3 ...). Put exactly ONE step per row. Do **NOT** use ranges like "1..3", "1-5", or collapse multiple steps into one row.
   - **Status** = "New"
   - **Type** = "Manual"
   - **Category** = the single best fit: "Positive" / "Negative" / "Workflow" / "Edge case" / "UI" / "Visual" / "Filter" / "Cross-Filter" / "Navigation" / "Load" / "Data Accuracy".
- Do **NOT** include explanations, code fences (like ```markdown), "Note:", or any text outside the table — EXCEPT the Coverage Summary section described below.

### Coverage Summary (Required)
After the table, append a section titled exactly:

## Coverage Summary

List, in concise bullet points, the scenarios already covered, **grouped by page and then by visual/category** (e.g. "Page 1 - Summary → MARKET bar: presence, sort, tooltip, cross-filter"). This is used to avoid regenerating duplicates in follow-up passes — be explicit about which page+visual+category combinations are done so remaining gaps are obvious.
