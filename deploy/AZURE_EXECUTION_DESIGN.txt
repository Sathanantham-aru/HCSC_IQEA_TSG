================================================================================
IQEA - TEST EXECUTION & REPORTING: LOCAL vs AZURE
Design / process document. No code written yet.
================================================================================

SUMMARY OF THE DECISION
-----------------------
Local  : keep the existing flow EXACTLY as it is. pytest runs in the venv,
         Chrome launches on the user's machine, `allure serve` opens the report
         in their browser. Nothing changes.

Azure  : do NOT execute in the container. Hand the script to the EXISTING CI
         pipeline, which already has Chrome, Java and the Allure CLI, and show
         the user the report link when it finishes.

         Crucially: this is done WITHOUT committing anything to git. GitLab can
         start a pipeline from data passed to its trigger API, so the
         generate -> run -> inspect -> regenerate loop leaves no trace in the
         repository. One deliberate commit happens at the end, only when the
         user is satisfied.

Two separate UI sections, each shown only where it works:
    execution_type=local  ->  "Execute & Report"              (existing)
    execution_type=azure  ->  "Execute & Report (CI Pipeline)" (new)


WHY NOT EXECUTE IN THE AZURE CONTAINER
--------------------------------------
Four independent blockers, each needing its own fix:

1. The generated script launches its own Chrome:
       options.add_argument("--start-maximized")
       driver = webdriver.Chrome(options=options)
   There is no Chrome or chromedriver in the app container. Installing them
   adds ~1 GB, and those flags lack --no-sandbox / --disable-dev-shm-usage, so
   it would fail with the same "Chrome instance exited" error we already fixed
   once.

2. Allure reports need JAVA. allure-pytest (pip) only writes raw JSON; turning
   it into a report requires the Allure CLI, a Java application. The image has
   no JRE and no CLI - confirmed, zero mentions in deploy/Dockerfile. So
   `allure serve` fails at "command not found".

3. Even with Java, `allure serve` starts its OWN web server on a random port
   and then tries to open a local browser. App Service publishes one port and
   there is no browser. The current code reports success while nothing happened.

4. subprocess.run(...) is synchronous, so the whole Streamlit app freezes for
   the length of the test run and App Service eventually times the request out.

The pipeline removes all four, because its runner already solves them.


PREREQUISITES - WHAT IS NEEDED BEFORE BUILDING
----------------------------------------------
[ ] P1. The GitLab project that will run the tests (id or full path).
        May be the same repo the scripts are pushed to today, or a dedicated
        one. A dedicated "test execution" project keeps noise away from the
        application repo.

[ ] P2. A pipeline TRIGGER TOKEN
        GitLab > Settings > CI/CD > Pipeline trigger tokens > Add.
        This is NOT the same as GITLAB_ACCESS_TOKEN. Supply it to the container
        as an App Service application setting, e.g. IQEA_CI_TRIGGER_TOKEN.

[ ] P3. The ref (branch) that holds .gitlab-ci.yml, e.g. main.
        The script itself is NOT on this branch - only the job definition is.

[ ] P4. A runner image with: python 3.12, Chrome + chromedriver, a JRE, and the
        Allure CLI. If your current pipeline already produces Allure reports,
        this exists - reuse it.

[ ] P5. DECISION: how the user reaches the report. See "REPORT ACCESS" below.

[ ] P6. DECISION: artifact retention (expire_in). A week is usually plenty for
        a generate-and-check loop.


THE DEPENDENCY PROBLEM - READ THIS, IT DRIVES THE DESIGN
--------------------------------------------------------
Generated tests are NOT self-contained. A real example:

    from output.page_file_generator.Mckesson_Home    import Mckesson_Home
    from output.page_file_generator.Mckesson_compare import Mckesson_compare
    from output.page_file_generator.Mckesson_product import Mckesson_product

So sending "the script" is not enough. The pipeline needs:
  * the test file itself
  * every page-object file it imports
  * those files at the SAME relative path (output/page_file_generator/...)
  * the job's working directory on PYTHONPATH so `output.page_file_generator.X`
    resolves (Python 3 namespace packages mean no __init__.py is required)

Approach: IQEA parses the test file's imports, pulls each referenced page file
from the database, builds a tar.gz containing the correct directory layout,
base64-encodes it, and sends it as ONE pipeline variable. The job un-tars it
into the job workspace and runs pytest from there.

Size: a test plus three or four page files gzips to a few KB, comfortably
inside GitLab's variable limits. If a bundle ever grows too large (many page
objects, embedded test data), fall back to the Package Registry route in
"ALTERNATIVES" below - the flow is otherwise identical.


================================================================================
THE AZURE FLOW, STEP BY STEP
================================================================================

PHASE 1 - SELECT
----------------
1.1  New section renders only when execution_type=azure.
1.2  User picks a generated test file. In Azure source=database, so the list
     comes from the Testfile table, not the filesystem.
1.3  IQEA loads the script content from the DB.
1.4  IQEA parses its imports and resolves each page-object dependency from the
     Pagefile table.
1.5  Show the user what will run: test name, the page files detected, the
     target project and ref. If a page file cannot be found, STOP here and say
     which one - better than a pipeline failing on ImportError five minutes
     later.

PHASE 2 - CONFIRM
-----------------
2.1  Confirmation prompt, stating plainly:
       - the script will run in the CI pipeline, not in Azure
       - NOTHING will be committed to git
       - roughly how long it takes (queue + runner start + test)
2.2  User confirms. Nothing has happened yet up to this point.

PHASE 3 - TRIGGER
-----------------
3.1  IQEA builds the bundle: tar.gz of
         run/<test_name>.py
         run/output/page_file_generator/<each page file>.py
     then base64-encodes it.
3.2  Generate an IQEA_RUN_ID (uuid) so this run can be identified in logs and
     in the UI.
3.3  Call the GitLab trigger API (python-gitlab is already a dependency):

         POST /projects/:id/trigger/pipeline
              token = <IQEA_CI_TRIGGER_TOKEN>
              ref   = main
              variables[IQEA_BUNDLE_B64]  = <base64 tar.gz>
              variables[IQEA_SCRIPT_NAME] = <test_name>.py
              variables[IQEA_RUN_ID]      = <uuid>

3.4  GitLab responds with a pipeline id and web_url. Store both in session
     state and show the pipeline link immediately, so the user can always get
     to it even if they navigate away.
3.5  NO COMMIT, NO BRANCH, NO PUSH. This is the whole point.

PHASE 4 - WAIT
--------------
4.1  Poll the pipeline status: created -> pending -> running -> success /
     failed / canceled.
4.2  Show a progress line with elapsed time and current stage. Poll every
     5-10 seconds; a CI queue does not move faster than that.
4.3  The poll must NOT block Streamlit (the existing local flow's mistake).
     Either a short auto-rerun loop or a background thread that updates
     session state.
4.4  Always offer a "stop waiting" escape - the user can come back to the
     pipeline link later. Long queues must not trap them in the page.

PHASE 5 - REPORT
----------------
5.1  On a terminal status, fetch the job from the pipeline and read its id.
5.2  Build the report URL (see REPORT ACCESS) and show:
       - status badge (passed / failed) and duration
       - link to the Allure report
       - link to the pipeline / job
       - the tail of the job log, so a failure is diagnosable without leaving
         IQEA. This matters most when the script itself is wrong, which is
         exactly what the user is checking.

PHASE 6 - ITERATE
-----------------
6.1  If the report looks wrong, the user regenerates the script and returns to
     Phase 2. Each attempt is a fresh pipeline and leaves NOTHING in git, so
     the loop can run as many times as needed.
6.2  When satisfied, a SEPARATE explicit action - "Commit this script to the
     repository" - uses the existing push_file_to_gitlab(). Exactly one commit,
     containing the version the user approved.

     Keeping trial runs and the final commit as different actions is the
     point: the commit history then shows approved scripts only, not the
     twenty attempts that led to each one.


================================================================================
THE PIPELINE JOB (their side, .gitlab-ci.yml)
================================================================================
Add ONE job. It must not disturb existing pipelines - the `rules` clause below
means it only ever runs for IQEA-triggered pipelines, because
$IQEA_BUNDLE_B64 is set by nothing else.

    iqea_adhoc_test:
      stage: test
      rules:
        - if: '$IQEA_BUNDLE_B64'      # IQEA-triggered runs only
      image: <your existing python+chrome+java+allure runner image>
      variables:
        PYTHONPATH: "$CI_PROJECT_DIR/run"
      script:
        - mkdir -p run
        - echo "$IQEA_BUNDLE_B64" | base64 -d | tar xz -C run
        - pip install -r requirements.txt
        - cd run
        - pytest -q --alluredir=../allure-results "$IQEA_SCRIPT_NAME" || true
        - cd ..
        - allure generate allure-results -o allure-report --clean
      artifacts:
        when: always              # a FAILED test must still publish its report
        paths:
          - allure-report
          - allure-results
        expire_in: 1 week

Notes
  * `|| true` on pytest: a failing test is a legitimate outcome the user needs
    to see. Without it the job aborts and `allure generate` never runs, so a
    failed test would produce no report at all - the one case where the report
    matters most.
  * `when: always` on artifacts, for the same reason.
  * PYTHONPATH points at the unpacked directory so the page-object imports
    resolve.
  * Chrome in CI needs --no-sandbox and --disable-dev-shm-usage. The generated
    script does NOT pass them. Either the runner image sets CHROME flags via
    env, or the job drops in a conftest.py that merges them - see OPEN ITEM O1.


================================================================================
REPORT ACCESS - DECISION NEEDED (P5)
================================================================================
An Allure report is a multi-file site that loads its data over XHR, so it
cannot be inlined into a Streamlit component. Three options:

 A. Job artifact URL (simplest)
        https://<gitlab>/<group>/<project>/-/jobs/<job_id>/artifacts/file/allure-report/index.html
    Works immediately, no extra setup. But on a PRIVATE project the user must
    be logged into GitLab. Fine if everyone has an account.

 B. GitLab Pages
    Nicer URLs, and access can be configured separately. Needs Pages enabled
    and a publish job.

 C. Pull the artifact into IQEA
    IQEA downloads the artifact zip via the API (using GITLAB_ACCESS_TOKEN,
    so the user needs no GitLab access at all), then either offers it as a
    download or serves it through an nginx /report/ route and iframes it -
    the same pattern already used for noVNC.

    Most work, but the only option where a user without a GitLab account can
    view the report. If IQEA is meant to be usable by people outside the QE
    team, this is the one.


================================================================================
OPEN ITEMS
================================================================================
O1. Chrome flags in CI. The generated script hardcodes only
    "--start-maximized". In a container Chrome needs --no-sandbox and
    --disable-dev-shm-usage or it exits immediately. Decide: fix the script
    GENERATOR to emit container-safe flags, or inject a conftest.py in the
    job. Injecting keeps generated scripts portable to a developer laptop,
    which is why the same approach was chosen for the live browser.

O2. Does the runner have outbound access to the application under test? A
    private staging URL reachable from a laptop may not be reachable from a
    shared runner.

O3. Concurrency. Several users triggering runs at once is fine for GitLab, but
    confirm runner capacity so attempts do not queue for a long time.

O4. Secrets. If a test needs credentials, they must come from GitLab CI
    variables, not be baked into the generated script.

O5. Cost/quota. Each trial run consumes CI minutes. A tight regenerate loop
    could get expensive on a shared quota - worth knowing the budget.


================================================================================
ALTERNATIVES CONSIDERED
================================================================================
Package Registry instead of a variable
    Upload the bundle as a generic package, trigger with the package URL, job
    downloads it. Removes any size limit. Use if bundles outgrow variables.
    Still zero commits.

Single force-pushed scratch branch
    Keep one `iqea-scratch` branch, force-push each attempt. History stays one
    commit deep and main is untouched. Simpler (no trigger token) but it IS
    still a git write, and concurrent users would fight over the branch.

Throwaway branch per run, deleted afterwards
    Works, but creates churn and needs cleanup - the problem you wanted to
    avoid.

Execute in the Azure container
    Rejected: see the four blockers at the top. Would need Chrome (~1 GB), a
    JRE and the Allure CLI (~250 MB) added to an image already carrying
    Playwright's Chromium, on a 2 GB App Service plan.


================================================================================
WHAT STAYS EXACTLY AS IT IS
================================================================================
The local flow is untouched: pytest in the venv, local Chrome, `allure serve`.
No behaviour change, no new dependency, no new configuration. The new section
is additive and only appears when execution_type=azure.

#                                                                              #
#  PART 2 - THE FRAMEWORK REPOSITORY                                           #
#  Generating code that drops into a real framework, for four stacks            #
#                                                                              #
################################################################################

THE GOAL
--------
Today IQEA generates a test that is self-contained and IQEA-shaped:

    from output.page_file_generator.jan_sauce_demo_login import jan_sauce_demo_login

    @pytest.fixture(scope="function")
    def setup_driver():
        options = Options()
        options.add_argument("--start-maximized")
        driver = webdriver.Chrome(options=options)      # test makes its own browser

...and a page object that re-implements its own waiting:

    def get_element(self, by, locator, timeout=10):
        return WebDriverWait(self.driver, timeout).until(
            EC.presence_of_element_located((by, locator)))

The goal is generated code that instead SLOTS INTO the existing framework:
page objects that are only locators and accessors, and tests that consume the
framework's driver fixture. That requires IQEA to know, at generation time,
which framework it is targeting and what that framework's conventions are.


--------------------------------------------------------------------------------
2.1  DIRECTORIES, NOT BRANCHES
--------------------------------------------------------------------------------
The original proposal was one branch per combination:
    python-selenium / python-playwright / java-selenium / java-playwright

RECOMMENDATION: use ONE branch with four directories instead.

Why branches are the wrong axis for this
  * Four branches holding four DIFFERENT projects can never be merged, so
    `main` stops meaning anything and every cross-branch diff is noise.
  * A shared improvement - a better BasePage wait, a new Allure helper - has to
    be applied by hand four times, forever, and will drift.
  * CI rules become branch-coupled, so one trigger cannot run two frameworks.
  * Contributors cannot tell which branch is "current"; there is no main line.

Proposed layout (repo: IQEA)

    frameworks/
      python-selenium/
        requirements.txt
        conftest.py                 <- OWNS driver creation
        pages/base_page.py          <- OWNS waiting/locator helpers
        pages/                      <- IQEA writes generated page objects here
        tests/                      <- IQEA writes generated tests here
      python-playwright/
        requirements.txt
        conftest.py                 <- owns browser/context/page fixtures
        pages/base_page.py
        pages/  tests/
      java-selenium/
        pom.xml
        src/test/java/base/BaseTest.java
        src/main/java/pages/BasePage.java
        src/main/java/pages/        <- generated page objects
        src/test/java/tests/        <- generated tests
      java-playwright/
        pom.xml
        src/test/java/base/BaseTest.java
        src/main/java/pages/  src/test/java/tests/
    .gitlab-ci.yml                  <- ONE pipeline, FRAMEWORK variable

Four separate REPOS is also defensible if each framework is genuinely
standalone and owned by different people. Four branches of one repo is the
option to avoid.


--------------------------------------------------------------------------------
2.2  THE HIGHEST-VALUE CHANGE: THE FRAMEWORK OWNS THE DRIVER
--------------------------------------------------------------------------------
This one change removes several problems at once, so do it first.

Today the generated test creates its own browser. Because of that:
  * Chrome flags are baked into generated code, so container-safety
    (--no-sandbox, --disable-dev-shm-usage) has to be solved by the GENERATOR -
    this is open item O1.
  * Running against a Grid instead of local Chrome would need the generator to
    emit different code again.
  * Every generated test repeats the same fixture, and any fix must be
    regenerated everywhere.

If the generated test instead consumes the framework's fixture:

    def test_successful_login(driver, login_page):        # fixtures from conftest
        ...

then:
  * flags, headless/headed, local vs Grid, timeouts and screenshot-on-failure
    are configured ONCE per framework, by people who own that framework
  * O1 disappears - it is no longer a generator concern
  * generated code shrinks to the part a human actually needs to review: the
    steps and the assertions

Same for page objects. `get_element()` with its own WebDriverWait should come
from the framework's BasePage, so a generated page object is only:

    class SauceDemoLogin(BasePage):
        USER_NAME  = (By.ID, "user-name")
        PASSWORD   = (By.ID, "password")
        LOGIN      = (By.ID, "login-button")

        def enter_username(self, value): self.type(self.USER_NAME, value)

CONTRACT TO DEFINE PER FRAMEWORK (this is the real specification work):
  * name of the driver/page fixture the test should request
  * BasePage class name, import path, and the helper methods it offers
  * whether locators are class constants or inline
  * screenshot/attachment helper to use on failure


--------------------------------------------------------------------------------
2.3  WHAT "FEED THE FRAMEWORK DETAILS" ACTUALLY MEANS
--------------------------------------------------------------------------------
The differences are much wider than import paths. Per combination:

                    python-selenium   python-playwright  java-selenium      java-playwright
  test runner       pytest            pytest             TestNG/JUnit       TestNG/JUnit
  browser handle    WebDriver         Page               WebDriver          Page
  locators          By.ID / By.XPATH  page.locator()     By.id()            page.locator()
  waiting           WebDriverWait+EC  AUTO-WAITING       WebDriverWait+EC   AUTO-WAITING
  assertions        assert            expect()           Assert.assertTrue  assertThat
  allure package    allure-pytest     allure-pytest      allure-testng      allure-testng
  dependencies      requirements.txt  requirements.txt   pom.xml            pom.xml
  file naming       snake_case.py     snake_case.py      PascalCase.java    PascalCase.java
  package decl      none              none               package ...;       package ...;
  page dir          pages/            pages/             src/main/java/...  src/main/java/...
  test dir          tests/            tests/             src/test/java/...  src/test/java/...

Two of these are not cosmetic:

  * PLAYWRIGHT AUTO-WAITS. Most explicit waits simply should not be generated.
    A Playwright page object with WebDriverWait-style helpers is wrong code
    that happens to work slowly. The prompt has to actively suppress them.
  * JAVA needs a package declaration matching its directory, and the FILE NAME
    must match the public class name or it will not compile. Generated Java
    therefore constrains the file name, unlike Python.

So each combination needs its own: prompt/template, target directories,
import & package convention, BasePage/fixture contract, and naming rule.
Recommendation: hold these in a per-framework descriptor (one file or DB row)
that the page generator and the test generator both read, rather than four
forks of the prompt.


--------------------------------------------------------------------------------
2.4  WHERE IQEA WRITES, AND HOW TRIAL RUNS STAY COMMIT-FREE
--------------------------------------------------------------------------------
Part 1's no-commit trigger and Part 2's real framework compose - there is no
need to choose.

TRIAL RUN (no commit)
  1. User picks framework + generated test.
  2. IQEA bundles the generated files WITH their framework-relative paths:
         pages/sauce_demo_login.py
         tests/test_sauce_demo_login.py
     (or src/main/java/pages/... for Java), tar.gz + base64.
  3. Trigger the pipeline with FRAMEWORK=python-selenium and the bundle.
  4. The job checks out the repo, copies the bundle OVER the framework
     directory, and runs. The framework's own conftest/BaseTest and
     requirements.txt are used, because they are already in the checkout.
  5. Report published as an artifact. Nothing committed.

APPROVED (one commit)
  6. When the user is satisfied, a separate explicit action pushes the same
     files via push_file_to_gitlab() into frameworks/<framework>/pages|tests.
     Exactly one commit, of the approved version only.

This is the answer to the original worry about commit churn: the iterate loop
writes nothing, and history contains approved scripts only.


--------------------------------------------------------------------------------
2.5  ONE PIPELINE, NOT FOUR   [SUPERSEDED BY D1 - SEE 2.9]
--------------------------------------------------------------------------------
NOTE: D1 chose four SEPARATE REPOS, so this section no longer applies. Each
repo carries its own .gitlab-ci.yml with a single job - no FRAMEWORK variable,
no extends matrix. Kept below only because the two rules at the end
(`|| true` and `when: always`) still matter, and because it documents why the
monorepo option was considered.

Four pipelines would share ~90% of their definition and drift apart. Use one
definition parameterised by FRAMEWORK.

    .gitlab-ci.yml

    workflow:
      rules:
        - if: '$IQEA_BUNDLE_B64'          # IQEA-triggered run
        - if: '$CI_PIPELINE_SOURCE == "push"'

    .iqea_base:
      rules:
        - if: '$IQEA_BUNDLE_B64 && $FRAMEWORK == $EXPECTED_FRAMEWORK'
      script:
        - cd frameworks/$FRAMEWORK
        - echo "$IQEA_BUNDLE_B64" | base64 -d | tar xz      # overlay generated files
        - !reference [.setup]
        - !reference [.run]
      artifacts:
        when: always                      # a FAILED test must still publish
        paths: [ "frameworks/$FRAMEWORK/allure-report" ]
        expire_in: 1 week

    python-selenium:
      extends: .iqea_base
      image: <python + chrome + java + allure>
      variables: { EXPECTED_FRAMEWORK: python-selenium }
      # setup: pip install -r requirements.txt
      # run:   pytest -q --alluredir=allure-results tests/ || true
      #        allure generate allure-results -o allure-report --clean

    java-selenium:
      extends: .iqea_base
      image: <maven + jdk + chrome + allure>
      variables: { EXPECTED_FRAMEWORK: java-selenium }
      # setup: mvn -B dependency:go-offline
      # run:   mvn -B test || true
      #        allure generate target/allure-results -o allure-report --clean

    ...python-playwright, java-playwright likewise

Keep from Part 1, for the same reasons:
  * `|| true` after the test command - a failing test is the outcome the user
    needs to SEE; without it the job aborts and no report is generated, in
    exactly the case where the report matters most
  * `when: always` on artifacts


--------------------------------------------------------------------------------
2.6  VALIDATE BEFORE THE PIPELINE
--------------------------------------------------------------------------------
LLM-generated code will sometimes not compile. Without a local check, every bad
generation costs a full CI cycle (queue + runner start + install).

  * Python: cheap and immediate - compile() or ast.parse() in IQEA before
    triggering. Catches most breakage for free.
  * Java: cannot be compiled without a JDK, which the Azure image does not
    have. Options: a fast "compile only" CI job (mvn -q test-compile) run
    before the full test job, or accept the cycle cost.

Either way IQEA should refuse to trigger when it already knows the code is
broken, and say why.


--------------------------------------------------------------------------------
2.7  NAMING AND COLLISIONS
--------------------------------------------------------------------------------
Two users generating a login page for two different applications both produce
LoginPage, and the second overwrites the first.

Needs a convention decided up front, e.g.
    pages/<app>/<page>.py           tests/<app>/test_<flow>.py
    src/main/java/pages/<app>/LoginPage.java

For Java this also fixes the package declaration, which must match the
directory. Applies to the DB too - the Pagefile/Testfile tables should carry
the app/framework so names are unique per app rather than globally.


--------------------------------------------------------------------------------
2.8  SEQUENCING - DO NOT BUILD FOUR AT ONCE
--------------------------------------------------------------------------------
Almost everything here is new and unproven: the framework repo, the trigger,
the bundle overlay, the report link, and framework-aware generation. Doing four
stacks simultaneously means debugging generation QUALITY and pipeline PLUMBING
at the same time, across four stacks - and when a run fails it will not be
obvious which layer caused it.

  Step 1  python-selenium only, end to end:
          framework repo dir, conftest owning the driver, BasePage, one
          pipeline job, trigger + poll + report link in IQEA, generator emitting
          framework-relative imports and using the fixture.
          -> proves the entire loop with the stack you already generate well.

  Step 2  python-playwright. Same language, new idioms. This is where the
          "suppress explicit waits" prompt work gets proven.

  Step 3  java-selenium. New build system, packages, file naming, TestNG.
          Biggest single jump - do it once the loop is trusted.

  Step 4  java-playwright. Mostly a merge of steps 2 and 3.


--------------------------------------------------------------------------------
2.9  DECISIONS - ANSWERED 2026-09-16
--------------------------------------------------------------------------------
[x] D1. FOUR SEPARATE REPOS, one per framework. Not directories, not branches.
        Starting with ONE new repo for python-selenium; the other three come
        later.
        Consequence: 2.5 ("one pipeline, not four") no longer applies as
        written. Each repo owns its own .gitlab-ci.yml, so there is no
        FRAMEWORK variable and no `extends` matrix - just one job per repo,
        which is simpler. IQEA needs a per-framework record of
        (repo id, ref, trigger token) instead of one repo plus a variable.
        Trade-off accepted: a BasePage improvement will not propagate between
        repos. With four independent repos each owns its own conventions,
        which is still far better than four branches that can never merge.

[x] D2. WE BUILD THE FRAMEWORK OURSELVES, to industry-standard shape, for the
        POC. No external owner to wait on - this was the item most likely to
        stall, and it is now unblocked.
        Consequence: because we define it, build it DRIVER-OWNED from day one
        (2.2). conftest.py creates the browser; generated tests only request
        the fixture. That closes open item O1 permanently rather than working
        around it - container flags, headless/headed and local-vs-Grid all
        become framework configuration that generated code never sees.

[x] D3. Uniqueness enforced by checking the FILE NAME in the database before
        saving, to avoid duplicates.
        Future direction: import an existing file FROM the repo, update it, and
        push it back. Worth noting now because it shapes the schema - if a
        generated file can later be round-tripped, the Pagefile/Testfile rows
        should carry the framework and the repo-relative path, not just a bare
        name. Cheap to add now, awkward to retrofit.

[x] D4. Viewers WILL have a GitLab login.
        Consequence: this is the simplification. Report access is Part 1
        option A - link straight to the job artifact:
          https://<gitlab>/<group>/<project>/-/jobs/<job_id>/artifacts/file/allure-report/index.html
        No artifact download, no nginx /report/ route, no token proxying, no
        serving a static site from the container. Part 1 option C is dropped.

[x] D5. Not a blocker - the user judges from the execution output, since
        reachability depends on the platform the script runs on.
        Still worth surfacing well: a connection failure to the application
        under test looks identical to a broken script. The job log tail in the
        UI (Phase 5.2) is what makes the difference visible, so keep it.

[x] D6. CI minutes are the user's call, BUT IQEA must show progress.
        Consequence: a new table to record pipeline execution progress.
        Designed in 2.10 below.


--------------------------------------------------------------------------------
2.10  EXECUTION TRACKING TABLE (from D6)
--------------------------------------------------------------------------------
WHY A TABLE, NOT SESSION STATE
  Streamlit session state dies on refresh, on navigation, and whenever the
  container restarts. A pipeline run outlives all three. Without persistence:
    * refreshing the page loses the run the user is waiting on
    * they cannot close the tab and come back to the report
    * there is no record of how many attempts a script took, which is exactly
      the visibility D6 asks for
  It also gives a "recent runs" view, so a user returning tomorrow can still
  reach yesterday's report.

PROPOSED SHAPE  (table: execution_run)

    id               pk
    run_id           uuid, the IQEA_RUN_ID sent to the pipeline - the join key
                     between IQEA and GitLab
    created_by       who triggered it
    framework        python-selenium | python-playwright | java-selenium |
                     java-playwright
    test_file_name   the generated test that was run
    page_files       names bundled with it (JSON list) - makes a failed
                     ImportError diagnosable after the fact
    project_path     GitLab project it was sent to
    pipeline_id      returned by the trigger API
    pipeline_url     web_url, shown immediately so the user always has a way in
    job_id           resolved once the job exists
    report_url       artifact URL, built once job_id is known
    status           queued | running | success | failed | canceled | unknown
    triggered_on     when IQEA called the API
    finished_on      when a terminal status was observed
    duration_secs    convenience, from GitLab
    log_tail         last N lines of the job log, for failures (see D5)
    attempt_of       optional self-reference: links regenerated attempts for
                     the same test, so "this took 5 tries" is answerable

KEEPING STATUS FRESH WITHOUT A DAEMON
  Nothing polls while the user's browser is closed, so rows can go stale. Do
  NOT add a background poller for this - it would keep running after the user
  has gone and burn API calls.

  Instead RECONCILE ON RENDER: whenever the Azure execution section loads,
  re-query GitLab for any row whose status is not terminal, and update it. The
  data is then correct exactly when someone is looking at it, which is the only
  time it matters. Cheap, no daemon, and it survives container restarts.

  While a user IS waiting, Phase 4's poll updates the same row, so the two
  paths converge on one source of truth.

WHAT THE UI SHOWS
  * current run: status, elapsed, pipeline link, and the report link when ready
  * recent runs for this user: newest first, each with its report link
  * attempt count per test file - the honest answer to "how many CI minutes
    did this cost", which is the point of D6
